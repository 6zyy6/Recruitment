# 权限与资料边界

本文依据已落盘核心、careers、Gmail/面试与模型代码；最终共享版测试和托管真实身份边界另行验收，不由历史结果代替。

应用角色来自 `lib/seed.ts` 的固定用户表：`hr`、`manager`、两名 `interviewer`、`admin`。`lib/server.ts#getUser` 用 Cookie 哈希在 D1 会话表中反查用户；客户端不能提交角色来取得权限。业务层 `applyAction` 还核对状态中的用户 ID/角色。当前没有组织、部门或租户 claim，HR 对整个演示库有权；这些公开账号只用于合成资料。

真实外部服务另有“允许操作者”，它不是应用角色：要求托管入口可信的 `oai-authenticated-user-id/email`，邮箱匹配服务端 `MAIL_OPERATOR_EMAIL`。live或配置非空AI key时内部登录和招聘读写也先检查操作者，之后仍受HR/经理/面试官角色限制。Gmail管理/发送始终检查操作者，不接受Demo Cookie、query/body邮箱或自行声明头作为替代。该保证依赖Sites入口认证/清除伪造头；直接本地请求不证明托管身份可靠。

live公开例外仅为careers开放职位/匿名新投递与两类token答复；无内部会话不等于有业务库读取权。careers只返回公开职位或本次最小回执，token仅对应本人核对/单场面试资料；匿名投递不调用收费模型、不自动发信。

| 返回路径 | 应用实际裁剪规则 | 现有证据 |
| --- | --- | --- |

## 数据库与托管边界

- D1业务/会话表以及Gmail按需建立的授权/state/mail_jobs均无RLS；Worker持有DB绑定，依靠服务端检查。D1运维权限可绕过投影，尚无独立运维访问审计。
- Sites public、应用角色、真实操作者、匿名新投递及两类token各有范围。live内部与Gmail使用托管身份头；公开careers与token端点不经过内部getUser，但有各自字段/幂等或令牌守卫，均不返回state。
- token 持有者就是该链接范围内的访问者；没有短信二次验证、真实候选人账号或收件邮箱所有权核验。重发、撤销、过期、已提交、Offer 后关闭和匿名化会使链接失效。
- 普通Origin检查允许缺失Origin，内部仍需身份/token，公开提交继续按白名单/同意/幂等校验；Gmail另有固定来源/state/PKCE。当前无全局限流/登录锁定；匿名联系方式未验证，不能据邮箱链接已有档案。非空AI key只开放给真实操作者+HR。
- `TEST_SITE_USER_ID/EMAIL`仅为本地烟测模拟可信入口，两项须同时配置且目标非loopback时拒绝；不是服务器授权配置，也不能证明线上能剥离伪造头或注入身份。
- 具体跨边界调用顺序及副作用见 [flows.md](./flows.md)；未验证项见 [tests.md](./tests.md)。
